# Guided ticket intake and inline dictation

## Implemented flow

1. **Ticket:** one Upload Your Ticket control reads a PDF (including scans), JPG or PNG immediately. An accessible indeterminate progress bar remains active while the upload/extraction request is pending, then completes only after a successful response. The populated ticket review appears immediately below it; no extra Next click is needed. There is an Enter details instead fallback. No provider/retention explanations or additional consent checkboxes appear in the booking flow.
2. **Arrival:** a ticket-style review shows the route, airline and flight number, with editable name, arrival airport, flight service date, passenger and luggage counts. Printed boarding/departure/arrival times, seat, gate, terminals, cabin, baggage allowance, booking reference and ticket number appear only when extracted. Supplementary values are labelled as printed, not live airline updates. Enter inside an input does not advance or save; use the explicit buttons. Next validates this step and confirms the reviewed flight details. All ticket-derived fields are applied in a single shared draft, including values shown on later steps. Next/Back preserves the same draft; a replacement ticket clears unknown suggestions across every step.
3. **Your ride:** choose a drop-off address/pin, add optional special instructions in one comment box and use its microphone to dictate. Structured accessibility/seat needs remain available under a collapsed options section. Save creates the request, then displays a brief confetti celebration (suppressed with reduced motion). Driver acceptance is still required to confirm a ride.

Extraction additionally returns timezone-aware arrival_at, explicitly booked luggage pieces and an explicit cab/hotel drop-off address if printed. There are no Ready to leave or arrival/local-time inputs in the normal successful extraction flow. Pickup readiness is calculated 30 minutes after the ticket's arrival time and sent as a timezone-aware UTC instant. If that time is missing, or the user edits flight number/date/airport, Next looks up the exact flight's scheduled arrival through the authenticated /flights/arrival endpoint. Flight fields are disabled while checking. Unchanged date-field events preserve extracted timing. A failed lookup keeps the review open and offers a full itinerary upload or confirmation of its printed landing date/time. Known Indian airports use IST automatically; other airports require an explicit UTC offset. This timing input appears only after an unavailable lookup, and no matching request is saved without a reliable time. Cancelled/diverted/incident errors cannot use this recovery. Times are never guessed. Flight date remains the service/departure date used by flight lookup, so overnight arrivals can have a different pickup date. Unknown luggage/count/time stays blank for review. A destination airport/city is never guessed as the cab drop-off; women-only eligibility and equipment are explicit choices.

Supplementary ticket details and booking identifiers remain in the in-memory review draft and are not sent in the saved ride request. The extraction endpoint does not persist these values or the raw upload. Provider processing policies still apply.

Uploads remain limited to 20 MB, unencrypted PDFs to three pages. Existing authentication, provider budgets and strict output validation remain. Upload and microphone actions initiate provider processing directly; raw uploads are transient, and provider policies still apply. This documentation records behavior without placing those implementation details inside the booking form.

Dictation stops automatically at 598 seconds to allow encoding headroom under the server's 600-second bound. Browser audio becomes mono 16 kHz PCM WAV. The server splits it losslessly into consecutive segments of at most 29 seconds, transcribes each using Sarvam and joins successful text in order. There are at most 21 provider calls per dictation. If any segment fails, the operation fails as a whole; the browser retains audio in memory for retry. Silence-only recordings fail usefully. Typed notes are preserved and transcription appends directly to the same editable box; Cancel discards only the recording. Notes support 2,000 characters, and longer transcripts remain visible until shortened rather than silently truncated.

There is no WAV upload, language picker, playback/review panel or separate Use these notes action. Language is automatically detected. Chunking retains every PCM frame but cannot guarantee recognition at word boundaries or AI accuracy. Longer recording/streaming can be added later if the product needs it; the current cap bounds memory, provider calls and endpoint timeouts. Browser microphone permissions, HTTPS and compatible recording/decoding remain required.

## Research and decisions

- [Groq vision](https://console.groq.com/docs/vision) documents image input and JSON mode. [Structured outputs](https://console.groq.com/docs/structured-outputs) distinguishes JSON syntax guarantees from schema guarantees. The integration uses the configured vision model plus local schema validation, temperature zero and an untrusted-document prompt. Review is mandatory because valid JSON cannot guarantee correct ticket interpretation.
- [pypdfium2's API](https://pypdfium2.readthedocs.io/en/stable/python_api.html) supplies PDF rendering. Readable digital tickets use embedded page text first, avoiding native rasterization. Scans or mixed text/scan files render every page to preserve visual labels. Digital text is bounded at 30,000 characters; larger documents require ticket-only pages. Each page is capped at 1800 pixels on its longest edge, resources are closed, and a process-local lock prevents concurrent calls into PDFium, which is not thread-safe. The added dependency is pinned in `backend/requirements.lock`. This is a library, not a prebuilt project.
- [MDN's recording guide](https://developer.mozilla.org/en-US/docs/Web/API/MediaStream_Recording_API/Using_the_MediaStream_Recording_API) and [working dictaphone example](https://mdn.github.io/dom-examples/media/web-dictaphone/) show the established `getUserMedia` → `MediaRecorder` → transcription pattern. The implementation is written for this app; no example project was imported. [MIME feature detection](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/isTypeSupported_static) avoids assuming one recorder codec across browsers. [Microphone requirements](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia) explain HTTPS and permission constraints.
- [Sarvam's REST contract](https://docs.sarvam.ai/api-reference/speech-to-text/transcribe) documents multipart uploads, the subscription-key header, `unknown` language detection, 30-second interactive requests and 16 kHz guidance. Retaining the existing WAV contract lets the backend independently validate duration and completeness without requiring FFmpeg. The configured `saaras:v3` remains supported; model selection remains a server setting.

- [GOV.UK question pages](https://design-system.service.gov.uk/patterns/question-pages/) recommends focused questions and related fields on a coherent step. The app now separates ticket intake, arrival review and ride details, rather than showing every booking/provider control together.
- [Sarvam API selection](https://docs.sarvam.ai/api/api-guides-tutorials/speech-to-text/which-api-to-use) distinguishes short REST requests, continuous streaming and longer batch jobs. For this bounded cab-instructions flow, server-side WAV segmentation reuses the existing authenticated endpoint without persistent batch jobs or a new WebSocket service.

## Setup and validation

Account and journey reads allow 30 seconds per attempt and retry a transport failure once. Successful account refresh clears its connection warning; Retry connection is available after a failed load. Form/upload errors remain separate, so background polling does not erase validation feedback. Writes, uploads and HTTP provider errors are never automatically replayed.

Configure server-only GROQ_API_KEY, a vision-capable GROQ_MODEL, SARVAM_API_KEY and SARVAM_MODEL; install backend requirements and restart. For central .environment/.env use scripts/sync_env.py. Groq and Grok/xAI are separate services; this repository uses Groq. Secrets must never enter NEXT_PUBLIC settings.

The frontend transcription timeout is 750 seconds for at most 21 sequential provider requests; configure production ingress accordingly; each individual provider request remains bounded at 30 seconds. Ticket extraction allows 90 seconds for upload, startup and provider processing. Flight lookup has a separate 30-request hourly budget per authenticated subject. It reuses the configured Aviationstack live-flight API and exact number/date/airport filtering; historical or distant future flights may not be available on the current provider plan. Scheduled arrival provides the baseline so existing delay polling applies the adjustment only once after booking. Cancelled, diverted or incident flights and missing/naive timestamps are rejected.

No database migration is required for the added extraction fields or notes limit (notes storage is already Text).

Automated coverage checks guided submission, retry idempotency, failed upload/save states, stale ticket clearing, automatic dictation/retry and microphone cleanup, timezone readiness, long WAV encoding, lossless 61-second splitting and failure of later provider segments. The ticket-review revision passed 130 backend tests in an isolated source snapshot and PostgreSQL/PostGIS database, 28 frontend tests, Ruff/format, lint/types, generated-contract checks and production build. Local synthetic browser review covers the step transitions and mobile layout; it does not prove real provider or target-phone behavior. Earlier deployed synthetic provider checks do not validate the new longer recording path. Signed-in end-to-end, multilingual long recordings on target phones and real ticket accuracy remain human verification tasks.
